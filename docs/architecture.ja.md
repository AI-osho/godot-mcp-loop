# godot-mcp-loop の構成と仕組み

[English](architecture.md) · [導入](getting-started.ja.md) · [サンプル](samples.ja.md)

対象：現行0.12.0（49ツール）と従来0.11.0（48ツール）。作品紹介は6本に揃え、最小platformerは内部の互換・試験用として保持します。

## ゲームを変更するだけでなく、変更後の動作を確かめる

godot-mcp-loopは、AIエージェントとGodot4をつなぐMCPサーバーとエディタアドオンです。中心になる使い方は「編集→実行→観察→判定」です。

エージェントはシーンやスクリプトを編集し、ゲームを起動して、Godotの入力イベントとしてキー・アクション・マウスを送ります。動いた結果は、状態値、条件待機、画面、ログ、宣言的な試験で確認します。入力を送ることと、資金・座標などの状態を直接書き換えることは別です。

これはゲーム制作のすべてを自動で完成させるサービスではありません。ルール、面白さ、絵、音、レベル設計は作者の判断と実装が必要です。ツールはその制作と確認を支援します。

## どの版で使えるか

| 機能 | 従来0.11.0 | 現行0.12.0 |
|---|---|---|
| シーン/ノード/スクリプト編集、実行、入力、観察、試験 | 利用可能 | 利用可能 |
| 原画依頼の記録、素材加工、プレビュー、検査、2D配置の7ツール | 利用可能（0.10.0から） | 利用可能 |
| 静的な導入診断doctor | 利用可能（0.11.0から） | 利用可能 |
| node_add_treeによる2D/UIの一括構築 | 含まない | 0.12.0から利用可能 |
| MCPツール数 | 48 | 49 |

`doctor`はMCPツールではなく、独立したコマンドです。公開版のサーバーと開発版のアドオンを混ぜないでください。サーバーとアドオンは同じ配布物/版を使います。

## クライアントからゲームまでの流れ

```text
MCPクライアント（Claude Code / Codex / Hermes等）
    │ 標準入出力（stdio）
    ▼
Node.jsのMCPサーバー
    ├─ 入力スキーマ・対象パス・実行条件の検査
    ├─ 対象プロジェクトを固定した処理
    ├─ シナリオの進行・結果のまとめ
    └─ 必要なときだけ固定された素材加工ワーカー
    │ 認証付きWebSocket、127.0.0.1
    ▼
Godotエディタのアドオン
    ├─ 編集中シーンの確認、nativeな編集/履歴、保存
    └─ Godot標準のデバッガ経路
        ▼
実行中ゲームのランタイムエージェント
    └─ 入力、状態取得、物理フレーム送り、画面、ログ
```

サーバーは、アドオンが作るセッション情報から接続先を見つけます。接続はセッションのトークンで認証し、ゲーム側に別の操作用ネットワークポートを追加しません。

エディタの操作とゲームの操作は別の層です。たとえば、`node_set`は編集するシーンを変え、`game_query`は実行中の値を読みます。シーンの変更を保存することも、ゲーム内の一時的な状態を変えることも、同じ操作ではありません。

## リポジトリのどこに何があるか

| パス | 役割 |
|---|---|
| `server/src/` | MCPの入口、接続、型・入力検査、各ツール、シナリオ実行 |
| `addons/mcp_loop/` | エディタ側ブリッジ、編集コマンド、ゲーム側ランタイム |
| `server/authoring/` | 任意のPNG加工に使う固定Python/Pillow処理 |
| `examples/` | リポジトリのプロジェクトで試せるゲームと試験用シーン |
| `samples/` | パッケージから単体コピーするゲーム。正本/生成物の関係は各設計文書で明示 |
| `server/test/` | TypeScript単体試験と、実Godotを使う結合試験 |
| `tests/godot/unit/` | Godot側の単体試験 |
| `docs/` | 導入、内部構成、ツール、シナリオ、安全性、公開手順 |
| `.claude/skills/godot-mcp-loop/` | エージェントへ道具の使い方を伝える同梱スキル |

サーバーをビルドしただけで、すでに起動中のMCPクライアントが新しいコードへ切り替わるわけではありません。配布物・アドオン・実行中サーバーの組み合わせを確認し、必要な再接続は利用者が行います。

## 機能を制作の流れで見る

### 1. シーンを作り、編集する

`scene_create`、`scene_open`、`scene_tree`で対象を作成/確認し、`node_add`、`node_set`などで編集します。スクリプトや入力設定も専用ツールから扱います。

0.12.0からの`node_add_tree`は、いま編集している空のNode2D/Controlシーンを明示して、小さな2D/UIの構成をまとめて追加するための道具です。追加は最大64ノード・深さ8で、使える型・プロパティ・値を限定します。3D全般、任意のスクリプト、任意のResourceを受け付ける汎用バッチではありません。

プレビューは追加せずに計画を検査します。適用は追加対象全体を一つの取り消し操作として記録し、保存は別の`scene_save`で行います。「編集した」「保存した」「保存後に読み直せた」は別々に確認します。

### 2. 絵を用意し、ゲーム向けに加工する

原画はクライアント側の既存の承認済み手段で作ります。MCPサーバーが画像APIの認証を取得したり、画像生成を内蔵していたりするわけではありません。

`production_plan`で制作方針を記録し、`art_request`で依頼を作り、返ってきたPNGを`art_register`で記録します。その後、`asset_build`で切り出し・拡大縮小・透過処理・アトラス化などを行い、`asset_preview`、`asset_verify`で見た目と変更の有無を確認します。`asset_scene_add`は検査済みの絵を標準のSprite2D等へ配置します。

PNG加工には任意のPython3.11以降とPillow13.0.0が必要です。従来の編集/実行機能やnode_add_treeのために、これらを新規導入する必要はありません。サーバーが勝手に依存をインストールすることもありません。

### 3. 起動して、操作し、観察する

`game_run`でゲームを起動し、`game_input`で入力を送ります。値は`game_query`で読み、条件は`game_wait_for`で待ち、画面は`screenshot`、不具合は`logs_read`で調べます。3Dでは`game_in_view`、`game_ray`、`game_contacts`も使います。

短いタイミングの現象を確かめるときは、`game_pause`と`game_step`で物理フレームを管理できます。後から値を一度だけ読むのではなく、入力中の値を記録する手段もあります。

`game_set`や`game_call`は、再現条件や制御された試験の準備に使えます。ただし、それでボスを消した結果を、通常操作で倒した証拠として扱ってはいけません。

### 4. 同じ確認を繰り返せる形にする

`scenario_run`はYAML/JSONの入力・待機・比較などを順に実行します。失敗したステップでは、期待値と実際の値、必要に応じて画面などを残せます。`test_run`はGUT/GdUnit4の試験実行を扱います。

試験の成功、画面の可読性、実際の音、人の遊び心地は別の評価です。終了コードが0でもnativeエラーがあれば成功とは扱わず、音が鳴っているフラグだけで実際の音を確認したことにもしません。

### 5. 設定を診断し、書き出す

`doctor`は設定や版ずれなどを静的に診断します。エディタを起動したり、接続したり、修復したりはしません。「設定は正常」と「実行時に接続/動作した」は別です。

`project_export`は既存のエクスポートプリセットから書き出します。シェルコマンドを自由に実行するツールではありません。書き出しテンプレート等の前提は利用者が用意します。

## なぜプレビュー・取り消し・保存を分けるか

プレビューは事前検査、取り消しはMCPが記録した編集の復元、保存はディスク上のファイルへの反映です。全編集や複数ファイルをまとめた完全な取引と同じではありません。人があとで行った編集まで勝手に戻しません。

通信が途切れた場合も、エディタへ要求を送った後では適用済みか分からない場合があります。その状態を「何も変更されなかった」に置き換えず、実際のシーンを調べてから次を判断します。編集を自動再送して二重に追加しません。

## サンプルと検証用シーンの位置付け

blocks、shooter、action、rpg、marble-3d、tower-defenseの6作品を同じ形式で紹介します。
各作品は操作・再挑戦・観察・試験を揃え、既存作のルール・素材・入力・リソースパスは保全します。
最小platformerは既存の既定シーンと試験の互換性のために残し、作品紹介からは外しています。

単体コピーと組込例の正本の方向、TDの論理画面サイズと移動後のテクスチャ参照の修正は
[変更点](sample-upgrades.ja.md)にまとめています。構築計画で作るノードと、別途制作するゲームロジック・絵・音は区別します。
通常入力・勝敗・終了の検査と、制御用フックによる試験も同じ証拠として扱いません。

公開パッケージの同梱内容は[導入の版別表](getting-started.ja.md#配布状態)で確認できます。
ソースにある機能を公開済みと案内せず、最終配布物の検証と独立した公開レビューを分けます。

## 安全性の前提

接続はlocalhostとセッション認証で制限し、ファイル操作ではプロジェクトの範囲や保護先を検査します。これらは、信頼していないゲームやプラグインをOSから隔離する機能ではありません。スクリプトの読み込み・検証、ゲームや試験の実行は、プロジェクトのコードを動かし得ます。

自分が信頼できるプロジェクトだけを開き、クライアント側の承認設定も使ってください。生成した記録・画像・検証結果は、ユーザーの資格情報や既存ゲームのセーブと分けて扱います。
